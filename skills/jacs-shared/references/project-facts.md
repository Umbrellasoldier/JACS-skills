# Project facts

Use an author-supplied profile to define the scientific scope, not to manufacture results.
For a substantial new section, create or reuse a compact ledger:

| Field | Purpose |
|---|---|
| `claim_id`, `statement` | The scientific statement being drafted. |
| `status` | `observed`, `derived`, `planned`, or `unknown`. |
| `source`, `locator` | Author file, table, figure, or run summary and precise location. |
| `quantity`, `value`, `unit`, `conditions` | Where relevant, what was measured and under which conditions. |
| `population`, `denominator`, `exclusions` | Where relevant, the evaluation population and filtering. |
| `selection_protocol`, `validation_stage` | Where relevant, reference use and completed scientific checks. |

The project can supply only the applicable fields. Do not block a supported one-sentence
edit because a whole-project ledger is absent. Resolve routine naming from established
source usage; ask only about a consequential unresolved ambiguity. Update the ledger when
the author corrects a fact or canonical term.

Keep unpublished project evidence local. A public template has empty fact collections;
examples must be clearly synthetic. Package release tests must not require private paths,
checkpoints, calculations, or proprietary datasets.
